## 6. 서로 충돌하는 규칙 (재검수로 5건 확정)

### 6-1. ⚠️⚠️ "다음 단계" 버튼 표기 — 가장 크고 반복적으로 등장하는 충돌

관련 ID(발생 순): V1-P11-009(11p) → V1-P23-002/003/004(23p) → V1-P24-001(24p) → V1-P39-005(39p) → V1-P40-002(40p) → V1-P43-002(43p)

- **11p(V1-P11-009)**: "화살표·아이콘 **단독** 버튼을 두지 않는다" — 단독(텍스트 없는) 버튼만 금지, 텍스트+화살표 조합 자체를 금지하진 않음(참고용, 직접 충돌은 아님).
- **23p(V1-P23-002~004)**: "다음: 확인 →"를 BEFORE로 제시하고, 그 화면에서는 "확인" 버튼과 동작이 100% 중복되어 "다음" 버튼 자체를 **완전히 제거**함. — 이건 "이 화면 한정 중복 버튼 제거" 사례.
- **24p(V1-P24-001)**: "화살표(→)는 모든 버튼에서 사용하지 않는다. **"다음: 액티비티"처럼 콜론(:)으로 다음 단계를 안내한다**" — 화살표만 금지, 콜론+화면명 형식은 **표준으로 명시적 허용**.
- **39p(V1-P39-005)**: "다음: 확인 →"를 BEFORE로, **"확인"만 AFTER**로 제시(콜론 형식 자체가 없어짐).
- **40p(V1-P40-002)**: "다음 단계로 이동" 버튼의 표준 형식은 **"다음: 액티비티"/"다음: 확인"**(콜론+화면명), 금지는 화살표뿐.
- **43p(V1-P43-002)**: DO — "버튼은 "확인", "동선 수정"처럼 짧게, **다음 단계는 콜론(:)으로 안내한다**" (24p·40p와 동일 방향 재확인).

**검수 결론**: 24p·40p·43p(3곳)가 "콜론+화면명 형식은 유지, 화살표만 금지"로 일관되게 명시하고, 39p·23p(사실상 1.5곳 — 23p는 특정 사례)만 다른 결과를 보여줌. **문서 내 다수 규칙은 "다음: 화면명" 형식 유지 + 화살표만 제거**로 수렴됨. 다만 39p가 명확히 "확인"만 AFTER로 적어둔 것은 여전히 표기상 모순으로 남음 — **PDF 작성자에게 재확인이 필요한 원본 문서 자체의 결함**.

**코드와의 관계**: 이번 세션에 `EventSelectView.jsx`("다음: 기간·숙소"→"기간·숙소")와 `ActivityPreferenceView.jsx`("다음: 동선 스타일"→"동선 스타일")에서 콜론+화면명 형식 자체를 없앴음 — 이는 다수 규칙(24p/40p/43p)과 다른 방향. **사람이 "콜론 형식을 되살릴지" 결정해야 함.**

### 6-2. ⚠️ 동선 확인 화면 버튼 개수 (3개 vs 2개)

관련 ID: V1-P08-001(8p, 대표수정 9) / V1-P11-002(11p, 체크리스트)

- 가이드는 "목록 열기"·"동선 수정"·"다음: 확정" 3버튼을 "동선 수정"·"확인" 2버튼으로 줄이는 것을 **명시적으로 확정(AFTER·확정)**함(8p), 11p 체크리스트도 동일하게 "2개로 정리"를 명시.
- 이번 세션에서 사용자가 **"동선보기" 버튼을 다시 추가해달라고 명시적으로 요청**하여 `ScheduleTableView.jsx`/`ItineraryView.jsx`가 현재 3버튼("동선보기"/"동선 수정"/"확인") 상태임.
- **가이드(2개, "목록 열기" 완전 제거)와 사용자의 최근 실제 요구사항(3개, 지도 화면 접근 수단 필요)이 정면으로 배치**됨 — 사람이 판단해야 할 항목.

### 6-3. ⚠️ "동선" vs "일정" 용어 통일

관련 ID: V1-P41-008(41p, 용어 고정) / V1-P39-003(39p, "일정 만들기" 확정) / **V1-P14-009(14p, H1 예시 "여행 일정을 확인해요") — 이번 검수에서 새로 연결한 근거** / V1-P41-009(41p, 화면 제목 예시도 "여행 일정을 확인해요")

- 41p는 "일정/루트/코스" 대신 반드시 "동선"으로 통일하라고 명시.
- 그런데 39p의 확정 버튼명이 "일정 만들기"이고, 41p 바로 그 페이지의 다른 예시(V1-P41-009)와 **14p의 H1 타이포 예시(V1-P14-009)조차 "여행 일정을 확인해요"로 "일정"을 쓰고 있음** — 가이드 자체가 자기모순.
- 실제 코드베이스도 "나의 일정"/"일정 만들기"/"여행 일정" 등 "일정"을 광범위하게 사용 중.
- **검수 결론**: "동선"(지도 위 이동 경로)과 "일정"(여행 전체 일자별 계획)이 서로 다른 개념을 가리키는 것으로 실무상 구분해 쓰고 있을 가능성이 높으나, 가이드 원문은 이 구분을 설명하지 않고 "일정" 자체를 금지어처럼 서술함 — **용어 정의 자체를 사람이 다시 정리해야 함**.

### 6-4. ⚠️ 헤더 높이 56px 규정 vs 이번 세션 조정(48px)

관련 ID: V1-P18-002(18p, 헤더 높이 56px) / (세션 작업 — AppHeader.module.css 패딩 14px→10px 변경)

- 18p가 헤더 높이를 정확히 56px로 명시. 예전 코드(패딩 14px)는 정확히 이 값을 만족했으나, 이번 세션에 사용자의 "너무 길어 보인다" 피드백으로 패딩을 10px로 줄이면서 48px가 되어 **8px 벗어남**.
- **검수 결론**: 가이드 수치(56px)와 사용자의 최근 시각적 피드백(더 짧게)이 상충 — 어느 쪽을 기준으로 삼을지 결정 필요.

### 6-5. ⚠️ 폰트 패밀리 — 맑은 고딕(가이드) vs Google Fonts(코드)

관련 ID: V1-P14-001~003(14p, 타이포그래피 서체 규정)

- 가이드는 "맑은 고딕(Malgun Gothic)" + "Apple SD Gothic Neo"(둘 다 시스템 폰트)를 지정.
- 실제 코드는 전 화면에서 Google Fonts(IBM Plex Sans KR·Urbanist·Inter)를 `@import`. **수치 차이가 아니라 폰트 자체가 다른 근본적 불일치.**
- 이 항목은 다른 화면 간 "충돌"이 아니라 **가이드 vs 코드의 직접 충돌**이라 6-1~6-3과 성격이 다르지만, "사람이 정해야 할 결정 사항"이라는 점에서 함께 분류함.

**⚠️ 참고 — 이전에는 "충돌"로 분류됐으나 재검수 결과 충돌이 아닌 것으로 정정된 항목**: V1-P04-001(정보 확인 팝업)과 V1-P05-001(약관 모달)은 `01` 문서에서 "가이드는 X만 유지인데 실제로는 팝업 자체를 삭제해서 더 강하게 갔다"고 적었으나, 이는 방향이 반대가 아니라 **가이드보다 더 단순화한 상위호환**이므로 엄밀히는 "충돌"이 아니라 "가이드 요구사항을 초과 달성"으로 재분류하는 것이 정확함. 다만 원본 파일의 표현을 임의로 고치지 않고, 여기서는 이렇게 결론만 정정해서 남겨둠(원본 `01` 문서의 문구는 그대로 유지됨).
